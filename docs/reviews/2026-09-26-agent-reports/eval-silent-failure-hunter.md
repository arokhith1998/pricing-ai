# Silent-failure hunt: Pricekeel (C:\Pricing-AI)

## Verdict

The ingest, governance, and CRM layers hold the line well: LoadReport, DecisionStore, and crm.py readiness counts are exactly the pattern this product needs, every drop and degrade is counted and surfaced. The weak layer is the copilot/RAG/matching stack, where the LLM-adjacent code was written defensively against crashes but not against silence. Several except-Exception-return-empty sites carry zero logging, and one path (copilot's opportunity extractors) does not even need an exception to go silent: a missing or renamed key in the analysis dict reads as a real zero via get-or-0, which then reads as "no opportunity" with no trace anywhere. The RAG web-search flag conflates "web not needed" with "web search failed," which is the exact failure this product exists to prevent in other people's pipelines. None of this is a blocker on deterministic pricing math (ingest.py, governance.py, crm.py are honest and load-bearing), but the copilot/matching/mapping layers should not ship a "no opportunities found" or "no competitor match" screen without a way to tell the difference between "the data says nothing" and "the code went quiet."

## Top findings (ranked)

1. BLOCKER, pricing/copilot.py, all opp_ extractors (_safe() at 138-145, _opp_excess_leakage 205-213, _opp_off_policy 252-259, _opp_quarter_end 392-397, _opp_defended_wins 161-168). Trigger: any missing or renamed key in the analysis dict (a diagnostic.py refactor, a stale cached payload, a JSON round-trip that drops a key), no exception required. lk.get(excess_vs_segment_reference_won) or 0 turns "key absent" into "value is zero," and if excess <= 0 return None drops the opportunity. User sees: a clean copilot answer saying "no opportunities" or that the book looks healthy, instead of "the analysis payload is malformed." Fix: replace the get-or-0 pattern with a sentinel that distinguishes missing from zero, and raise or log or flag degraded=True when a required key is absent instead of silently defaulting to a number that also decides not to render.

2. BLOCKER, pricing/rag.py lines 60-146 (web_search, _web_perplexity, _web_tavily) plus api/main.py:687 and web/src/components/ChatPanel.tsx:339. Trigger: user checks "use web," a provider key is set, but the call times out, 401s, or 500s. Both _web_perplexity and _web_tavily catch bare Exception and return an empty list with zero logging. rag.ask() then sets used_web = bool(web_hits) which is False. User sees: an answer with no web citations and usedWeb false, indistinguishable from "the assistant decided it did not need the web." No log line anywhere tells an operator the web provider is broken. Fix: log the exception with the provider name (never the query, to stay in the privacy contract), and return a tri-state reason (ok / not_configured / error) that the API and UI can render as "web search failed" versus "web not used."

3. MAJOR, pricing/copilot.py _opp_raise_prices:298-302, _opp_over_discounted_slices:350-355, _opp_investigate:422-426. Trigger: analysis["realization_by_segment"] or hierarchy_slices[dim] arrives as something that raises on .to_dict(orient=records) (for example a malformed dict after an API JSON round-trip). except Exception: return [] / continue / return None, no logging anywhere in the module (no logging import at all in copilot.py). User sees: an empty opportunity list for "where should we raise prices" or "which products are over-discounted," reading as "no headroom" instead of "the analysis shape was unexpected." Fix: log with the dimension/qid, and thread a degraded note onto the Answer so the UI shows "opportunity extraction degraded for this lens" instead of a clean empty state.

4. MAJOR, pricing/matching.py extract_plans_from_url:437-443 and extract_plans_from_text:373-396. Trigger: a competitor URL is blocked by the SSRF guard, blocked by robots.txt, network-fails, or the LLM returns malformed JSON. Both paths swallow and return (fallback_vendor, []) per URL with no logging and no per-URL status carried into Comparison. compare() then just shows zero competitor plans for that vendor. User sees: "no matches" or a comparison missing a competitor entirely, unable to tell "we could not legally or technically fetch that page" from "that page genuinely has no plans." Fix: return a per-URL status (ok / blocked / fetch_error / parse_error) and surface it in Comparison as a warnings list.

5. MAJOR, pricing/mapping.py lines 318-331, Layer 4 cloud LLM fallback in map_headers. Trigger: assist.has_llm() is true but assist.map_columns() raises (provider timeout, malformed JSON not fixable by the code-fence strip, a raised LLMUnavailableError). except Exception: pass swallows it with no logging; the column just stays in unmapped_columns with no distinguishing note. User sees, in the /map-headers review UI: "we could not confidently map these columns," same as if the LLM genuinely found nothing, when in fact the LLM never returned a real answer. Fix: log the exception and add a flag such as llm_fallback_failed true to the map_headers result so onboarding support can tell a provider outage from a genuinely odd header.

6. MINOR, api/main.py:384 and api/main.py:405, HTTPException(status_code=400, detail=f"Could not read file: {exc}"). Trigger: a malformed CSV or XLSX upload that raises inside pandas parsing. The raw exception string (pandas or openpyxl internals, occasionally including byte offsets or internal buffer state) reaches the client unfiltered. Low risk since the buffer is in-memory with no filesystem paths, but it is still internal error text leaking into an HTTP response. Fix: log the exception server-side with exc_info=True, return a fixed message such as "could not parse this file as CSV or XLSX."

7. MINOR, pricing/model.py:73, X[c] = pd.to_numeric(col, errors=coerce) inside prepare(). Trigger: a NUMERIC feature column (discount_pct, term_months, quantity, is_quarter_end, competitor_present) contains a value that fails numeric coercion after enrich() (for example a caller passing a raw frame directly, bypassing ingest.enrich's own reporting). Silently becomes NaN; LightGBM tolerates NaN splits but TrainedModel.metrics never counts how many values were coerced, so a systematically dirty feature column degrades the win-probability model with nothing in the metrics to show it. Fix: count NaNs introduced by this coercion per column and add to TrainedModel.metrics.

8. NIT, pricing/rag.py:53-54, retrieve_doc_chunks: chunks with c.embedding is None are skipped with no count. Currently unreachable in practice since docs.py's embed_texts embeds all chunks from an upload in one batch call that either succeeds for all or raises for the whole request, so a partially-embedded chunk list should not occur today. Flagging as residual risk if a future partial-embedding or resumable-upload path is added.

## What's genuinely good

- pricing/governance.py DecisionStore.insert (109-162): database failure logs a warning with logger.warning, degrades to an in-memory row, and returns persisted false on the response so the caller's UI can show the decision was not durably stored. This is the reference pattern the rest of the codebase should copy.
- pricing/ingest.py LoadReport end to end: every blank-row drop, duplicate drop, ID conflict, excluded-open-deal count, blank-booked count, mixed-currency warning, and ambiguous date-order assumption is counted and rendered in summary() before any number reaches the dashboard. This is explainability-first ingestion done right.
- pricing/crm.py analyze_records (212-260): the readiness block reports closed_received versus closed_usable versus closed_excluded_missing_value (and the open-deal equivalents), plus _guard_degenerate_list and _currency_guard fail loudly with CRMDataError rather than silently rendering a confident-looking zero-leakage book.

## Fix next week

Replace the get-key-or-0 / _safe(default=0.0) pattern across pricing/copilot.py's opportunity extractors with a real missing-versus-zero distinction, and add logging to copilot.py, rag.py, mapping.py, and matching.py (none of the four currently import the logging module). That one change closes findings 1, 3, 4, and 5 outright and partially closes 2 (finding 2 still separately needs the tri-state web-search reason), and it is the highest-leverage fix because it is the one place a silent failure requires no exception at all to reach the user.
